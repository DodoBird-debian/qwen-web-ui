# Potential WebUI improvements

Make the first screen about what the user wants to do: describe an image, change a photo, or extend its edges. Bring the prompt and next action into view, show which image is being edited, and move request planning and GPU details behind controls people can find when they need them. Keep the existing editor, reference order, RunPod request contract, and access to both raw and composited results.

## What the current WebUI does

Reviewed the current checkout in Chromium at 1440 × 900 and 390 × 844. Checked the first screen, a prompt example, an inpaint source upload, the empty outpaint state, and a text-to-image submission using a mocked RunPod response. The external comparisons below come from the projects’ published app source, guides, and examples. They establish interface behavior, with no inference, quality, cost, or speed comparison implied.

| Task | Observed behavior | Usability issue |
| --- | --- | --- |
| Start a prompt on desktop | The first screen showed a large empty canvas. The prompt started about 669 px down and Generate at 826 px. The settings rail started with request planning, including image-count shortcuts, run type, and separate jobs. | The most important input gets less prominence than the empty results area. | Edit an image | Image edit requires an uploaded reference. Inpaint and Outpaint already have source-picker empty states. ## Recommended redesign

### P0 · Put the prompt and main action first

- **Desktop.** Put the prompt near the top of the main pane. Shrink the empty result canvas to a compact placeholder. Keep a visible row for the selected model, canvas size, transparency, and output count. Place results under the composer, with history adjacent or collapsed by default on smaller screens.
- **Phone.** Open on the workspace rather than the top of the references rail. Place the mode, prompt and primary action above the decorative canvas. References and settings can remain under the existing bottom navigation as jump targets or panels. Keep the action visible after editing and when the keyboard closes. When the keyboard is open, avoid covering text selection, validation, or the bottom navigation.
- **Labels.** Use **Generate image**, **Apply edit**, and **Extend canvas** for the three intents. Put the next fixable validation issue beside the action and make it link or focus the relevant input. Keep current keyboard shortcuts and live status messages.

**Implementation starting point.** Retain one mounted composer and one submit handler. Change the layout, responsive order, and navigation rather than cloning controls into mobile and desktop versions. Check the existing behavior that preserves focus while refreshing. [Layout](src/components/layout.ts) · [Responsive styles](src/styles/mobile.css) · [Navigation](src/components/mobile-navigation.ts) · [Submit and validation](src/app.ts)

### P0 · Explain what gets edited

- Present **Create** and **Edit** as the two top-level intents. In Edit, use **Whole image**, **Paint an area**, and **Extend edges** as direct choices over the existing modes. Preserve current shortcuts, crop and feather controls, and mode-specific inputs. Dropping an image in Create can offer **Use as reference** or **Edit this image** without switching silently.
- Put a clearly labelled **Source image** near the editor and supporting **References** near the instruction. With the painted/extend flow, show **Source · image 1**, **Guide · image 2**, then the user references. Show how many slots remain, including the two reserved guide slots. Keep the editable aliases and reference ordering. Make the generated guide separately inspectable.
- Offer **Match source** in the single-source whole-image path. Display the actual legal output size before running. Use the existing pixel and aspect checks to round or scale within worker limits, and label any scaling. Do not replace a manually chosen canvas size on every upload.
- Use plain validation such as “Paint one area or choose Whole image.” When displaying a composited result, explain that pixels outside the local mask are kept by the browser. Keep raw model output available and distinguish it in the viewer and metadata.

**Implementation starting point.** Map new UI labels to the existing editor modes and outpaint flag. Reuse source-picker, preparation and reference-remapping logic. [Mode and reference bindings](src/app.ts) · [Edit preparation](src/editor/prepare-edit.ts) · [Compositor](src/editor/inpaint.ts)

### P1 · Add model-aware presets and examples

- Show the active model as **Base** or **Turbo · 8 steps**, with the endpoint name and health in connection details. Use model and canvas size as separate controls. Keep **1024 quick preview**, **larger canvas**, and **Custom** as explicit sizes with actual dimensions. Retain exact numeric steps in Advanced. Keep the current Base default until a fixed-seed comparison on this deployment establishes a better one.
- Start with four local examples: text/logo layout, one-photo recolor, source plus supporting reference, and transparent product cutout. Each should load an editable instruction and the needed inputs, state the intended result, and wait for Generate. Use original or licensed sample assets bundled locally. Show the real ordered references and select an alpha-compatible format for the cutout example. Warn before replacing a nonempty draft.
- Offer short, optional writing prompts for **Change**, **Keep**, and **Use this from reference**. Show how they combine in the editable prompt. The first iteration can use deterministic text and existing tag insertion, without an automatic rewrite service.

**Implementation starting point.** Use existing defaults, validated settings, and reference APIs. Build the small preset list from allowed values. Keep Turbo’s step lock and independent Base settings when switching. [Settings](src/components/settings.ts) · [Contract](src/api/contract.ts) · [Reference prompt compiler](src/references/prompt-compiler.ts)

### P1 · Make cost, readiness, and recovery clear

- Put a small run summary beside Generate. For a normal run it can show **1 image · 1 request**. A frequent batch might show **10 images · 3 requests (4 + 4 + 2)**. Keep explicit grouping and comparison grids in a **Run options** panel rather than front-loading them. Derive both views from the same planner.
- Use a separate **Technical details** section for phase VRAM, offload, KV cache, payload bytes and request JSON. Surface actual blockers inline, including invalid tags, the 10 MB request limit, or an unresolved submission. Present VRAM as an estimate based on the configured profile. Distinguish submitted requests from possible parallel work inside each request.
- Show the current job and its stop controls in one consistent location. For a run of multiple requests, keep **Finish current request** and **Cancel current request** distinct. If submission is uncertain, show the known job ID or a clear next action. Preserve the existing guard against duplicate POSTs and avoid offering an automatic retry.

**Implementation starting point.** Reuse the immutable planner, job guard and activity components. Avoid driving a second request state machine from the summary. [Run controls](src/components/run-controls.ts) · [Submission guard](src/generation/submission-guard.ts) · [Run execution](src/generation/runner.ts) · [Activity](src/components/generation-activity.ts)

### P1 · Make the result a starting point

- Promote **Edit this image**, **Use as reference**, and a single clear download action. Put seed reuse, alternate downloads, metadata and export options in an accessible **More actions** menu. Keep ZIP and contact sheet available when selecting multiple results.
- For masked and extended edits, show the browser-composited result as the main preview, with the raw model image labelled and directly accessible. Keep the existing before/after inspector. State which variant is being passed into Edit and allow an explicit alternative. For partial results or encoding changes, show a short explanation beside the affected image or run and keep every usable result.
- Keep model, seed, delivered size and format visible in the inspector or metadata. A **Generate again** or **Reuse settings** action should clearly say whether it reuses the previous seed before it submits or prepares anything.

**Implementation starting point.** Reorganize action prominence on the existing result cards and use the current handlers for browser history, compositing, exports and seed reuse. [Result cards](src/components/results.ts) · [Inspector](src/inspection/viewer.ts) · [History](src/components/image-history.ts)

## How to validate the redesign

| Scenario | Acceptance check |
| --- | --- |
| Fresh create on 390 × 844 and 1440 × 900 | Prompt and Generate fit in the initial viewport of an empty configured workspace. Typing works with keyboard and touch. A missing connection or invalid input offers an actionable message. |
| One-photo edit and targeted edit | A user can find the source picker, explain the difference between whole-image and painted edits, and reach the right action from either a file or an existing result. Test cancel or undo of an accidental mode choice, and preserve ordered tags and the inpaint mask. |
| Load a cutout or multi-reference recipe | Loading sends zero jobs. The user can identify what each reference does. The prepared request includes only allowed fields, stays under the payload ceiling, and uses PNG or WebP for a transparent result. |
| Request 10 images and inspect Turbo | The same summary, request preview and dispatched plan show 4 + 4 + 2. Turbo remains locked to eight steps and returning to Base restores its previous steps and endpoint configuration. |
| Delivered partial or resized result | A mock response with mixed success retains usable cards, clearly distinguishes source/raw/composite, and offers the next edit without resubmitting anything. A keyboard user can reach every moved action. |
| Observe first-time use | Try Create, Edit part of a photo, and Make a transparent cutout with 3–5 people unfamiliar with the UI. Record time to first ready request, scroll before the first action, wrong-mode choices, and whether they can explain output count versus request count. Compare against the current layout using the same tasks and fixture images. This is a proposed study. |

Run the existing browser regressions for [mobile/editor interaction](tests/browser/interaction.spec.ts), [plan grouping](tests/browser/batch-planner.spec.ts), [Base and Turbo](tests/browser/endpoints.spec.ts), [job activity](tests/browser/generation-status.spec.ts), and [partial results](tests/browser/history.spec.ts). Add targeted browser assertions for the new first-screen layout and the example-loader path when implementing the redesign.

## Scope

The first release should cover the prompt-first layout and clearer edit scope. Presets, examples, result actions and the run summary can follow in smaller changes. Keep the exact request limits and existing async behavior: up to ten total reference inputs, one to four images per API request and a 10 MB request body. Painted and extended edits continue to send an ordinary source/guide pair within that limit. Generative alpha depends on the model and the delivered format. LoRA loading, native mask or strength fields, prompt-enhancer services, and porting other projects’ model runtimes fall outside this redesign. [Frozen request contract](src/api/contract.ts) · [Current compatibility and delivery notes](docs/inference-and-delivery.md)

## Additional features

These are new capabilities beyond the layout changes above. Start with a searchable shortlist and portable recipes. They improve repeated use of the existing studio and can be tested without running a model. A sketch editor is the next small feature aimed specifically at Qwen Image 2.1.

| Feature | What to add and where to start | First acceptance check |
| --- | --- | --- |
| **1. Search and shortlist results** · small | Search local history by prompt and filter by model, date or favorites. Star individual results and open a two-image comparison across different jobs. History already pages through job summaries, and the inspector already compares images within an edit. Use summary queries for search and fetch full images only when a result is opened. [History](src/components/history.ts) · [Job summaries](src/storage/job-summary.ts) · [Inspector](src/inspection/viewer.ts) | Star one result from a batch, leave the run, then find it by prompt and compare it with an image from a different job. Searching should avoid decoding result images. Stars should follow the existing session/persistence preference. |
| **2. Save and share a recipe** · medium | Add a versioned, loadable recipe with the selected model, explicit input settings, seed and reference roles. Our existing request JSON previews the worker request and ZIP exports describe delivered files. A recipe would reopen those choices in the editor. Save settings by default and let users explicitly include source, ordered refs and masks in a separate project bundle. Omit keys and endpoint credentials from both. Start with a JSON sidecar or bundle manifest. Consider an opt-in PNG recipe later, since re-encoding can strip embedded settings. [Workspace model](src/domain/workspace.ts) · [Existing ZIP export](src/export/archive.ts) · [ComfyUI’s recipe metadata](https://github.com/Comfy-Org/docs/blob/main/development/api-development/workflow-metadata.mdx) · [Fooocus gallery](https://github.com/ogoun/fooocus-qwen-image-2.1#gallery) | Export a painted edit, import it in a fresh browser tab, and recover its reference order, mask and exact seed. Importing sends zero requests. Exclude credentials, check missing references before running, and reject unsupported versions or oversized bundles before loading their images. |
| **3. Recover an unfinished draft** · medium | For users who enable browser storage, snapshot the current unsent prompt, settings, source, mask and references after edits settle. On reload, offer **Restore draft** or **Discard**. Keep drafts separate from named projects and from saved jobs. The existing project serializer and storage preference provide starting points. [Projects](src/components/projects.ts) · [Browser storage](src/storage/db.ts) | Close and reopen the tab mid-edit. Restore returns the draft without changing an existing saved project, starting a job, or storing any credential. Disabling browser storage leaves future drafts session-only. |
| **4. Reopen a series and fill gaps** · medium | Save a run record with its planned cells, endpoint, accepted job IDs and result links. We already recover jobs by ID, but the runner’s grid is kept in memory. Reopen the same series after reload and let the user explicitly start cells confirmed never submitted or omitted. Label failures and unresolved submissions separately. A manual retry of a failed request should show that it creates a new job. [Runner](src/generation/runner.ts) · [Submission guard](src/generation/submission-guard.ts) · [Image history](src/components/image-history.ts) | Interrupt a 4 + 4 + 2 run after the first batch completes and the second is accepted. Restore the grid and reconcile the known second job without reissuing it. Starting the remaining two images requires confirmation. An ambiguous POST without a job ID remains blocked until reconciled. |
| **5. Compare prompt variants** · medium | Add named prompt variants to complement the existing steps, CFG and seed axes. Start with one shared source, reference list, canvas and seed. A product photographer could compare three backgrounds while keeping the product instruction unchanged. Preview the substituted prompt and actual request count for each variant. Different prompts require separate requests. Keep the current run limits and existing result grid. [Generation plan](src/generation/plan.ts) · [Run controls](src/components/run-controls.ts) | Given three named prompts and a fixed seed, preview and send exactly three valid requests with the same references and seed. Keep each output labelled with the specific prompt it used. Mark differences in output as observations from the run. |
| **6. Draw a reference sketch in the browser** · small to medium | Add a blank sketch canvas with a basic palette, brush, eraser and undo. **Use as reference** turns the sketch into an ordinary uploaded PNG. Sketch edits stay separate from the inpaint region mask. Fooocus already offers this interaction and Qwen’s official Turbo example uses a yacht sketch as an image input. [Current reference import](src/references/images.ts) · [Fooocus sketch tool](https://github.com/ogoun/fooocus-qwen-image-2.1#reference-images) · [Qwen’s sketch example](https://github.com/QwenLM/Qwen-Image-2.1#qwen-image-21-turbo-8-step-generation-and-editing) | Draw, undo, then add a sketch and use its tag in a prompt. Count it as one reference toward the existing slot and payload limits. Cancelling leaves the draft and its mask untouched. Describe the sketch as visual guidance with variable adherence. |
| **7. Assemble transparent results on a canvas** · larger | Let the user place already-transparent outputs or uploaded cutouts over a background, move and scale them, and export a composite. Support a simple title layer when exact readable text matters. Kokon demonstrates how useful movable image layers can be. The browser version can start with assets that already have alpha and ordinary text overlays. Automatic object splitting and generated background fill require a separate pipeline. [Current compositing](src/editor/inpaint.ts) · [Kokon Layers Lab](https://kokon.app/image-to-layers/) | Place two alpha-bearing PNGs and a title over an opaque or transparent background. Change order and export locally. Verify pixel positions and transparent regions with fixtures. Preview and export send zero generation requests. |
| **8. Export a set of crops and sizes** · medium | Use one focus position to frame several outputs, such as a square PNG, a portrait WebP and a small preview. Allow per-variant crop overrides before packaging. Current export controls resize or trim a single image, and the gallery ZIP packages selected results. Connect those paths so the user can preview all derivatives, then write a ZIP with useful filenames and actual output metadata. [Export dialog](src/export/dialog.ts) · [Encoder](src/export/encode.ts) · [Archive builder](src/export/archive.ts) | One input produces the expected dimensions and formats in a single ZIP. Preview shows each crop boundary and warns when JPEG will flatten alpha. Each manifest entry matches the actual image. Too-large sets fail before allocating the whole archive. |

Keep features 1–3 under existing history, project and export actions. Sketch belongs in the reference picker. Put series recovery and prompt variants in Run options. The canvas composer and export sets can follow after the prompt-first layout is in use. These are additive browser workflows using the existing generation contract.
