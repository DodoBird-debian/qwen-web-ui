# Selected WebUI improvements

Keep the existing RunPod request contract and client-side edit guides.

## Editing and generation

### Explain what gets edited
- Present **Create** and **Edit** as the two top-level intents. In Edit, use **Whole image**, **Paint an area**, and **Extend edges** as direct choices over the existing modes. Preserve current shortcuts, crop and feather controls, and mode-specific inputs. Dropping an image in Create can offer **Use as reference** or **Edit this image** without switching silently.
- Put a clearly labelled **Source image** near the editor and supporting **References** near the instruction. With the painted/extend flow, show **Source · image 1**, **Guide · image 2**, then the user references. Show how many slots remain, including the two reserved guide slots. Keep the editable aliases and reference ordering. Make the generated guide separately inspectable.
- Offer **Match source** in the single-source whole-image path. Display the actual legal output size before running. Use the existing pixel and aspect checks to round or scale within worker limits, and label any scaling. Do not replace a manually chosen canvas size on every upload.
- Use plain validation such as “Paint one area or choose Whole image.” When displaying a composited result, explain that pixels outside the local mask are kept by the browser. Keep raw model output available and distinguish it in the viewer and metadata.

**Implementation starting point.** Map new UI labels to the existing editor modes and outpaint flag. Reuse source-picker, preparation and reference-remapping logic. [Mode and reference bindings](src/app.ts) · [Edit preparation](src/editor/prepare-edit.ts) · [Compositor](src/editor/inpaint.ts)

### Make cost, readiness, and recovery clear
- Put a small run summary beside Generate. For a normal run it can show **1 image · 1 request**. A frequent batch might show **10 images · 3 requests (4 + 4 + 2)**. Keep explicit grouping and comparison grids in a **Run options** panel rather than front-loading them. Derive both views from the same planner.
- Use a separate **Technical details** section for phase VRAM, offload, KV cache, payload bytes and request JSON. Surface actual blockers inline, including invalid tags, the 10 MB request limit, or an unresolved submission. Present VRAM as an estimate based on the configured profile. Distinguish submitted requests from possible parallel work inside each request.
- Show the current job and its stop controls in one consistent location. For a run of multiple requests, keep **Finish current request** and **Cancel current request** distinct. If submission is uncertain, show the known job ID or a clear next action. Preserve the existing guard against duplicate POSTs and avoid offering an automatic retry.

**Implementation starting point.** Reuse the immutable planner, job guard and activity components. Avoid driving a second request state machine from the summary. [Run controls](src/components/run-controls.ts) · [Submission guard](src/generation/submission-guard.ts) · [Run execution](src/generation/runner.ts) · [Activity](src/components/generation-activity.ts)

### Make the result a starting point
- Promote **Edit this image**, **Use as reference**, and a single clear download action. Put seed reuse, alternate downloads, metadata and export options in an accessible **More actions** menu. Keep ZIP and contact sheet available when selecting multiple results.
- For masked and extended edits, show the browser-composited result as the main preview, with the raw model image labelled and directly accessible. Keep the existing before/after inspector. State which variant is being passed into Edit and allow an explicit alternative. For partial results or encoding changes, show a short explanation beside the affected image or run and keep every usable result.
- Keep model, seed, delivered size and format visible in the inspector or metadata. A **Generate again** or **Reuse settings** action should clearly say whether it reuses the previous seed before it submits or prepares anything.

**Implementation starting point.** Reorganize action prominence on the existing result cards and use the current handlers for browser history, compositing, exports and seed reuse. [Result cards](src/components/results.ts) · [Inspector](src/inspection/viewer.ts) · [History](src/components/image-history.ts)

## Additional capabilities

| Feature | Behavior | Acceptance check |
| --- | --- | --- |
| **Recover an unfinished draft** · medium | For users who enable browser storage, snapshot the current unsent prompt, settings, source, mask and references after edits settle. On reload, offer **Restore draft** or **Discard**. Keep drafts separate from named projects and from saved jobs. The existing project serializer and storage preference provide starting points. [Projects](src/components/projects.ts) · [Browser storage](src/storage/db.ts) | Close and reopen the tab mid-edit. Restore returns the draft without changing an existing saved project, starting a job, or storing any credential. Disabling browser storage leaves future drafts session-only. |
| **Reopen a series and fill gaps** · medium | Save a run record with its planned cells, endpoint, accepted job IDs and result links. We already recover jobs by ID, but the runner’s grid is kept in memory. Reopen the same series after reload and let the user explicitly start cells confirmed never submitted or omitted. Label failures and unresolved submissions separately. A manual retry of a failed request should show that it creates a new job. [Runner](src/generation/runner.ts) · [Submission guard](src/generation/submission-guard.ts) · [Image history](src/components/image-history.ts) | Interrupt a 4 + 4 + 2 run after the first batch completes and the second is accepted. Restore the grid and reconcile the known second job without reissuing it. Starting the remaining two images requires confirmation. An ambiguous POST without a job ID remains blocked until reconciled. |
| **Compare prompt variants** · medium | Add named prompt variants to complement the existing steps, CFG and seed axes. Start with one shared source, reference list, canvas and seed. A product photographer could compare three backgrounds while keeping the product instruction unchanged. Preview the substituted prompt and actual request count for each variant. Different prompts require separate requests. Keep the current run limits and existing result grid. [Generation plan](src/generation/plan.ts) · [Run controls](src/components/run-controls.ts) | Given three named prompts and a fixed seed, preview and send exactly three valid requests with the same references and seed. Keep each output labelled with the specific prompt it used. Mark differences in output as observations from the run. |
| **Export a set of crops and sizes** · medium | Use one focus position to frame several outputs, such as a square PNG, a portrait WebP and a small preview. Allow per-variant crop overrides before packaging. Current export controls resize or trim a single image, and the gallery ZIP packages selected results. Connect those paths so the user can preview all derivatives, then write a ZIP with useful filenames and actual output metadata. [Export dialog](src/export/dialog.ts) · [Encoder](src/export/encode.ts) · [Archive builder](src/export/archive.ts) | One input produces the expected dimensions and formats in a single ZIP. Preview shows each crop boundary and warns when JPEG will flatten alpha. Each manifest entry matches the actual image. Too-large sets fail before allocating the whole archive. |
